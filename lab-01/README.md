# Звіт з лабораторної роботи 1: Середовище та професійний Git workflow

## Завдання 1. Git і редактор

**1. Чому значення `core.autocrlf` різне для Windows і Unix і що станеться, якщо його не задати?**
Різні операційні системи по-різному позначають кінець рядка у файлах. Windows використовує два символи — CRLF (`\r\n`), а Unix-подібні системи (macOS, Linux) використовують один — LF (`\n`).
Якщо в команді розробників зі змішаними ОС не налаштувати `core.autocrlf`, Git буде бачити зміну символу кінця рядка як зміну всього коду. Якщо розробник на Windows збереже файл і відправить його, усі рядки зміняться на CRLF. Коли розробник на Linux стягне цей код, його Git покаже, що змінено кожен рядок у файлі, що призведе до гігантських нечитабельних diff-ів та постійних конфліктів при злитті. На Windows значення `true` автоматично конвертує LF у CRLF при завантаженні коду і навпаки при збереженні.

**2. Чим історія з `pull.rebase=true` відрізняється від типової?**
Типовий `git pull` за замовчуванням виконує злиття (merge). Якщо ви зробили локальний коміт, і хтось інший теж зробив коміт на сервері, типовий pull створить додатковий "merge-коміт", щоб об'єднати ці гілки. Це робить історію комітів заплутаною і схожою на павутину.
Увімкнений параметр `pull.rebase=true` змінює цю поведінку: замість злиття Git тимчасово "відкладає" ваші локальні коміти, завантажує нові зміни з сервера, а потім "накладає" ваші коміти поверх них. Це забезпечує ідеально пряму (лінійну) та чисту історію проєкту без зайвих комітів злиття.

**Глобальні параметри Git (вивід `git config --list --global`):**
```text
user.name=Alina Skrypa
user.email=skrypa.alina@gmail.com
credential.helper=manager
init.defaultbranch=main
core.autocrlf=true
core.editor=code --wait
pull.rebase=true
```
## Завдання 2. Середовища виконання
Перевірка версій та перемикання:
PS C:\Users\Аліна> fnm use 18
PS C:\Users\Аліна> node -v
v18.20.8
PS C:\Users\Аліна> fnm use 20
PS C:\Users\Аліна> node -v
v20.20.2

PS C:\Users\Аліна> uv run python --version
Python 3.12.5

PS C:\Users\Аліна> docker compose version
Docker Compose version v2.30.0-desktop.1

Навіщо менеджер версій, коли проєктів більше одного?

Менеджер версій необхідний для ізоляції середовищ та уникнення конфліктів залежностей між проєктами. Різні проєкти часто вимагають різних, іноді несумісних версій інструментів (наприклад, старий проєкт може стабільно працювати лише на Node.js 18, тоді як новий потребує специфічних функцій Node.js 20+).
Встановлення однієї глобальної версії на рівні операційної системи неминуче зламає код або залежності в тих проєктах, які розраховані на іншу версію. Менеджери версій (як fnm для Node.js або uv для Python) дозволяють тримати на одному комп'ютері кілька ізольованих версій одночасно і миттєво перемикатися між ними під потреби конкретного проєкту, залишаючи глобальне середовище системи чистим.

## Завдання 3. GitHub і доступ
Профіль заповнено, двофакторну автентифікацію увімкнено. Згенеровано ключ ed25519 із парольною фразою.
Перевірка з'єднання по SSH:

Чому приватний ключ ніколи не потрапляє в репозиторій і що робити у разі витоку?
Приватний ключ — це еквівалент вашого пароля. Якщо він потрапить у репозиторій, будь-хто зможе автентифікуватися від вашого імені, отримати доступ до всіх ваших ресурсів або вносити шкідливий код у проєкти.
Послідовність дій, якщо приватний ключ потрапив у репозиторій:

**1.Негайно зайти в налаштування GitHub (SSH and GPG keys) та видалити скомпрометований публічний ключ, щоб відкликати доступ.
**2.Видалити скомпрометовану пару ключів локально зі свого комп'ютера.
**3.Згенерувати новий SSH-ключ та додати новий публічний ключ в акаунт GitHub.
**4.Видалити файл із приватним ключем з історії Git-репозиторію за допомогою утиліти git filter-repo або BFG Repo-Cleaner (звичайне видалення через git rm та новий коміт залишать файл в історії).

Виконати git push --force, щоб перезаписати історію на віддаленому сервері.

## Завдання 5. Правила репозиторію
Налаштовано ruleset для гілки main з правилами: Require a pull request before merging, Restrict force pushes, Restrict deletions, Require linear history.

Що зміниться в налаштуваннях, коли робота стане командною, і чому «заборона обходу правил» безпечна в команді й шкідлива соло?
Коли робота стане командною, ми увімкнемо обов'язкове схвалення від інших учасників (Require approvals) та обов'язкові перевірки статусів CI/CD конвеєра (Require status checks to pass).
Опція "Заборона обходу правил адміністратором" (Do not allow bypassing the above settings) шкідлива при соло-розробці, тому що автор Pull Request не може сам собі його затвердити. Увімкнувши її наодинці, можна заблокувати самому собі можливість зливати код в main. У команді ж ця заборона є обов'язковою та безпечною, адже вона гарантує, що навіть адміністратор репозиторію не зможе влити код в обхід перевірок та обов'язкової рецензії іншого розробника.
